description: Create the next weekly project as its own public GitHub repo, fully scaffolded
argument-hint: <short-project-name e.g. serverless-orders>

Create a new weekly project repository named by the user: **$ARGUMENTS** (a short kebab-case name; ask for one if missing).

Follow these steps exactly:

1. **Determine the project number.** Read `projects-log.md`; the next number is the highest `#` in the table + 1 (or 1 if the table is empty). The repo name is `project-XX-$ARGUMENTS` with XX zero-padded to two digits.

   **Check for a revisit week first.** If the next number N is a multiple of 5, this is a **revisit week** — no new project. Do all of the following, then stop:

   - **Add the revisit row to `projects-log.md`:** `#` = N, Repo = the project N-4 repo linked at its `revisit-w{N}` branch, Domain / Industry / Level copied from that project's row and suffixed `(revisit of #N-4)`, everything else `—`, Status `revisit`.
   - **This row is what advances the numbering.** Without it the next `/kickoff` reads the same highest `#` and computes N again — a multiple of 5 forever, so the framework could never issue project N+1. The row is not bookkeeping; it is the thing that makes the week end.
   - **Commit as** `chore: revisit week N — re-architect project N-4`.
   - **Tell the user:** re-architect project N-4 from its original `requirements.md` on a `revisit-w{N}` branch in that project's own repo, copying `templates/revisit-template.md` in as `revisit.md` (substituting `{Project Name}` and `{N}`), and run `/log-project` back here once the re-score is done.
   - **Scaffold nothing.** No directory, no GitHub repo — the revisit lives on a branch of a repo that already exists.

2. **Check prerequisites.** Run `gh auth status`. If not authenticated, stop and tell the user to run `! gh auth login` first.

3. **Create the sibling directory** `../project-XX-$ARGUMENTS` (under the same parent as this hub) and scaffold it:

   **Files from templates:**
   - `CLAUDE.md` ← `templates/CLAUDE-md-template.md`
   - `checklist.md` ← `templates/weekly-checklist-template.md`
   - `retrospective.md` ← `templates/retrospective-template.md`
   - `README.md` ← `templates/README-template.md`
   - `analysis/requirements-restated.md` ← `templates/requirements-restated-template.md`
   - `analysis/qualifiers-constraints.md` ← `templates/qualifiers-constraints-template.md`
   - `analysis/assumptions.md` ← `templates/assumptions-template.md`
   - `analysis/clarification-interview.md` ← `templates/clarification-interview-template.md`
   - `analysis/current-state.md` ← `templates/current-state-template.md` *(L3+ only — scaffolded always, deleted by the user on greenfield projects once `/new-project` announces the level)*
   - `analysis/disposition-7rs.md` ← `templates/disposition-7rs-template.md` *(same)*
   - `design/design-review.md` ← `templates/design-review-template.md`
   - `design/decisions.md` ← `templates/decisions-template.md`

   **Copied wholesale:**
   - `prompts/` ← the hub's entire `prompts/` folder (8 files), so the repo is self-contained
   - `.claude/commands/` ← the hub's `templates/claude-commands/` (**8 files**: new-project, client, diagram, defend, test-plan, fault-drill, evaluate, linkedin)

   **Empty dirs with `.gitkeep`:** `requirements/`, `iac/`, `iac/evidence/`, `iac/evidence/console/`

   **Context snapshot:**
   - `.project-context.md` ← a copy of the hub's `projects-log.md`, prefixed with one line: `> Snapshot taken at kickoff of project XX — input for the Selection Rule in prompts/01.` Include the Recurring Weaknesses and Domain Rotation sections; prompt 01 reads all three.

   **`.gitignore`** with standard CDK/Python/Node ignores (`cdk.out/`, `node_modules/`, `.venv/`, `__pycache__/`, `*.js.map`) plus `iac/.fault-drill.md` — the fault drill's sealed answer must never be committed where it can be read early.

   **Substitute the placeholder last.** Once every file is in place, replace every occurrence of `{Project Name}` with `project-XX-$ARGUMENTS` across the **whole scaffolded tree** — the templates carry it, and so do the copied `prompts/`. Then verify none survive: `grep -rn '{Project Name}' .` must return nothing.

   This is not cosmetic. The cost-allocation tag in `checklist.md` and `design/decisions.md`, and the Cost Explorer filter in `prompts/04-test-plan.md`, all resolve through this placeholder — and the tag applied by the CDK has to match the filter exactly. A placeholder left literal silently breaks the estimate-vs-actual loop, which is the one thing `/log-project` checks for at close-out.

   **Do not** create `requirements/requirements.md`, `.acceptance-tests.md`, `.reference-solution.md`, or `.change-request.md` — all four are generated by `/new-project` inside the project repo.

4. **Create the GitHub repo and push:** in the new directory run `git init -b main`, commit everything as `chore: kickoff project XX from framework hub`, then `gh repo create project-XX-$ARGUMENTS --public --source . --push`.

5. **Register it in the hub:** add a row to `projects-log.md` with the number and the repo name as a GitHub link; leave Domain, Industry, Level, Score, Pillars, Raised dimension, Beat ref, and Next-week focus as `—` (filled by `/new-project`'s selection and later by `/log-project`); Status `kicked off`. Commit as `chore: kickoff project XX`.

6. **Tell the user:** the repo URL, and that the next step is to open Claude Code inside the new project directory and run `/new-project`. If this is project 01, point them at the **One-Time Setup** block at the top of `checklist.md` first — `cdk deploy` will fail later without `cdk bootstrap`, and the cost-allocation tag needs ~24h to activate.

**Boundary reminder:** do NOT generate requirements, select the domain or level, or do any Stage 1 work here. That happens via `/new-project` inside the project repo, where `CLAUDE.md` carries the full boundary list.
